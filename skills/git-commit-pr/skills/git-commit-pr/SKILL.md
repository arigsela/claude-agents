# Git Commit & PR Workflow

## When This Skill Triggers

This skill MUST be used whenever Claude is:
- Fixing a bug or issue in a file within a git repository
- Implementing a feature or enhancement
- Updating configuration files (Terraform, Helm, GHA workflows, Dockerfiles, etc.)
- Refactoring or modifying any tracked file
- Applying a code change the user has requested or approved

**Trigger signals**: Any time Claude uses `str_replace`, `create_file`, or `bash_tool` to modify/create files that are inside a git repository, this workflow MUST be followed instead of just editing files in place.

**Do NOT trigger** when:
- The user is just asking Claude to review or explain code (read-only)
- The user explicitly says they'll handle git themselves
- Files are outside a git repo (e.g., `/home/claude/` scratch work)
- The user says "just edit it" or "don't make a PR"

## Prerequisites

Before starting, verify these tools are available:

```bash
git --version
gh --version
```

If `gh` is not installed or not authenticated, inform the user and provide setup instructions:
```bash
# Install gh CLI
# Auth: gh auth login
```

## Workflow

### Step 1: Stash Any Uncommitted Work

Before switching branches, protect any existing work:

```bash
cd <repo-root>
git stash --include-untracked 2>/dev/null || true
```

### Step 2: Checkout Main and Pull Latest

```bash
git checkout main
git pull origin main
```

If `main` doesn't exist, try `master`. If neither exists, abort and ask the user which base branch to use.

### Step 3: Create a Feature Branch

Generate a descriptive branch name from the change being made:

```bash
git checkout -b feature/<short-description>
```

**Branch naming rules:**
- Prefix: `feature/`
- Description: lowercase, hyphen-separated, concise summary of the change
- Max 50 characters for the description portion
- Examples:
  - `feature/fix-argocd-sync-alert`
  - `feature/update-eks-node-group-size`
  - `feature/add-health-check-endpoint`
  - `feature/update-gha-deploy-workflow`

### Step 4: Apply the Code Changes

Make the actual file modifications using `str_replace`, `create_file`, or `bash_tool` as needed. All changes happen on the feature branch.

### Step 5: Stage and Commit

```bash
git add -A
git commit -m "<type>: <concise description of change>"
```

**Commit message format:**
- Use conventional commit prefixes: `fix:`, `feat:`, `chore:`, `docs:`, `refactor:`, `ci:`, `perf:`, `test:`
- Keep the subject line under 72 characters
- Be specific about what changed and why
- Examples:
  - `fix: resolve ArgoCD sync timeout on staging deployments`
  - `feat: add retry logic to Deploy GHA workflow`
  - `chore: bump Terraform provider version to 5.x`
  - `ci: add linting step to PR validation workflow`

### Step 6: Push the Branch

```bash
git push origin feature/<short-description>
```

### Step 7: Create the Pull Request

Use `gh` CLI to create the PR:

```bash
gh pr create \
  --base main \
  --head feature/<short-description> \
  --title "<Same as commit message subject>" \
  --body "<auto-generated description>" \
  --label "claude-generated"
```

**PR description auto-generation rules:**

The PR body should follow this structure:

```markdown
## Summary
<1-2 sentence summary of what this PR does and why>

## Changes
<Bulleted list of specific changes made>

## Context
<Brief explanation of the problem or motivation, drawn from the conversation with the user>

---
*This PR was auto-generated by Claude.*
```

**Labels:**
- Always apply: `claude-generated`
- If the label doesn't exist in the repo, create it first:
  ```bash
  gh label create "claude-generated" --description "PR created by Claude AI" --color "7C3AED" 2>/dev/null || true
  ```
- If the change type is obvious, also add contextual labels if they exist in the repo (e.g., `bug`, `enhancement`, `infrastructure`, `ci`)

### Step 8: Report Back

After the PR is created, provide the user with:
- The PR URL
- A brief summary of what was changed
- The branch name for reference

Example output:
```
✅ PR created: https://github.com/artemishealth/<repo>/pull/123
   Branch: feature/fix-argocd-sync-alert
   Changes: Fixed ArgoCD sync timeout by increasing the retry window from 30s to 120s in the staging app-of-apps config.
```

## Error Handling

| Scenario | Action |
|----------|--------|
| Branch already exists | Append a short suffix: `feature/<desc>-v2` or ask the user |
| Merge conflicts on main | Inform the user, do not force-push or auto-resolve |
| `gh` not authenticated | Print `gh auth login` instructions and stop |
| Push rejected | Check if branch protection rules apply, inform the user |
| No changes detected | Inform the user that there are no changes to commit |
| Label creation fails | Continue without the label, don't block the PR |
| Dirty working tree on start | Stash changes, inform the user what was stashed |

---

## Important Safety Rules

1. **Never force-push** (`git push --force`) unless the user explicitly asks for it
2. **Never push directly to main** — always use a feature branch
3. **Never auto-merge** — the PR is for review, not auto-completion
4. **Preserve the user's existing work** — always stash before switching branches
5. **If anything fails, stop and report** — don't silently continue past errors
6. **Ask before rebasing** — if main has diverged, ask the user how they want to handle it
